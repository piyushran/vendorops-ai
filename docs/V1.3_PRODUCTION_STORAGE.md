# V1.3 Production Object Storage

V1.3 adds an S3-compatible object-storage backend behind the existing storage abstraction.

## Goals

- Keep the application independent of a specific object-storage vendor.
- Preserve the local backend for development and deterministic tests.
- Support S3-compatible providers through standard AWS credentials and endpoint settings.
- Keep storage keys tenant-scoped by construction.
- Preserve the existing `UploadedFile.storage_path` and `GeneratedReport.storage_path` contract by storing a stable `s3://bucket/key` URI.

## Configuration

```env
STORAGE_BACKEND=s3
S3_BUCKET=vendorops
S3_REGION=ap-south-1
S3_ENDPOINT_URL=
S3_ACCESS_KEY_ID=
S3_SECRET_ACCESS_KEY=
S3_SESSION_TOKEN=
S3_PRESIGNED_URL_TTL_SECONDS=900
```

`S3_ENDPOINT_URL` may be set for S3-compatible providers such as MinIO. When it is empty, the AWS SDK uses the normal regional S3 endpoint.

## Storage key layout

Tenant-owned objects should use keys in the following form:

```text
organizations/{organization_id}/workspaces/{workspace_id}/files/{file_id}/{filename}
organizations/{organization_id}/workspaces/{workspace_id}/reports/{report_id}/{filename}
```

The storage layer does not infer tenant identity from arbitrary paths; callers provide the complete key.

## Security notes

- Do not commit cloud credentials.
- Prefer workload identity / IAM roles in deployed environments over long-lived access keys.
- Keep the bucket private.
- Use short-lived pre-signed URLs for customer downloads when direct object access is introduced.
- Enable server-side encryption and bucket versioning in the cloud environment.
