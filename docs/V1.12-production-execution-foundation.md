# V1.12 — Production Execution Foundation

## Objective

Promote the V1.11 governed execution contract from process-local state to a production-safe execution substrate that can survive restarts, run across multiple workers, and reconcile ambiguous external side effects.

## Non-negotiable invariants

1. Authorization is evaluated immediately before execution; no connector bypass exists.
2. Every consequential action has an organization, workspace, actor, tool identity/version, action fingerprint, and idempotency key.
3. Idempotency is enforced by the database, not an in-memory cache.
4. Only one worker may own an execution attempt at a time through an expiring lease/claim.
5. A worker crash never silently turns an execution into an unknown success/failure.
6. An external side effect is considered complete only after independent verification or explicit reconciliation.
7. Receipts and audit events are durable and tenant-scoped.
8. Retries reuse the same external idempotency key; they never generate a new key for the same logical action.

## State machine

`REQUESTED -> EXECUTING -> VERIFYING -> SUCCEEDED`

Failure paths:

- transient adapter failure -> retry while attempts remain
- exhausted retry budget -> `FAILED`
- authorization failure -> `REJECTED`
- lease expiry during external execution -> `UNKNOWN`/reconciliation required
- verification mismatch -> reconciliation required; never report success

## Persistence

Reuse the existing `agent_runs` and `tool_executions` tables introduced by the durable agent execution migration. Add the missing execution ownership/verification fields only where required; do not create a second execution database.

Required database guarantees:

- unique idempotency key per tenant/workspace execution namespace
- indexed status + lease expiry for recovery workers
- durable attempt records
- durable output/verification payloads
- approval/action fingerprint binding

## Concurrency model

Workers claim a requested/retryable execution using an atomic database operation and an expiring lease. The lease owner and expiry are persisted. A second worker cannot claim an actively leased execution.

Expired leases become recoverable. Recovery must first reconcile with the connector using the original idempotency key before attempting another external write.

## External side-effect boundary

Database idempotency alone cannot guarantee exactly-once behavior when the external system is not part of the same transaction. Every production connector must therefore support one of:

- a provider-native idempotency key,
- a deterministic external reference that can be queried before retry,
- or a reconciliation/read-back contract that proves whether the intended side effect already occurred.

Business Central integration must implement this boundary before financial writes are enabled.

## Audit

Emit durable events for at least:

- authorization decision
- execution requested
- execution claimed
- attempt started
- adapter response received
- verification result
- retry scheduled
- terminal success/failure/reconciliation required

All events must carry organization/workspace, execution id, idempotency key, actor, tool identity and timestamps.

## Acceptance tests

- duplicate requests across two engine instances produce one logical execution
- process restart preserves receipt lookup
- concurrent workers cannot both own the same execution
- expired leases are recoverable
- retry preserves the original idempotency key
- crash after external success is resolved through reconciliation, not blind retry
- rejected writes never invoke an adapter
- approval fingerprint mismatch never invokes an adapter
- successful external writes require independent verification before `SUCCEEDED`
- audit history remains available after process restart

## Business Central exit criterion

V1.12 is considered integration-ready when the execution engine can safely hand an approved invoice write to a Business Central connector and recover from worker crashes without risking a duplicate invoice.
